# Edge Cases

Real situations Contract 1.2 (ADR-0030, ADR-0053) cannot yet cleanly represent. Each is
logged for later contract review as v2 backlog. **No final schema solution is
invented here.**

**Decision status** is one of:

- **provisionally usable** — can be entered today with the noted treatment.
- **open until pilot** — treatment stays undecided until real pilot data exists.
- **assumption at risk** — a current schema assumption likely to fail; expect a
  contract change.

| Case | Current treatment | Model limitation | Decision status | Contract review needed |
| --- | --- | --- | --- | --- |
| Joint development | Keep principal `companyId`; store confirmed role details in program/regimen `relationships`. | Relationship UI is not implemented. | provisionally usable | Yes |
| Regional rights | Store confirmed territories and rights in program/regimen `relationships`. | Relationship UI is not implemented. | provisionally usable | Yes |
| Licensing transfer | Update principal `companyId` when it changes; store current confirmed program/regimen relationships. | No relationship history in a current-state snapshot. | provisionally usable | Yes |
| Company acquisition | Point records to the surviving/controlling entity; keep asset/program IDs stable. | No parent/successor modeling. | provisionally usable | Yes |
| Company or asset rename | Update `assetName`; keep the stable `assetId`; record the former name as a `former-name` alias. | Resolved for assets by typed `aliases` (ADR-0030); company former-name aliases remain a future item. | provisionally usable | No |
| Salts | Treat as the same asset identity unless clearly a distinct program; document. | No salt distinction in `assetId`. | open until pilot | Yes |
| Prodrugs | Provisionally distinct asset when developed as a distinct molecule; document. | Prodrug/parent relationship unmodeled. | open until pilot | Yes |
| Conjugates | Provisionally distinct asset; document conjugate identity. | Conjugate identity rules undefined. | open until pilot | Yes |
| Fixed-dose combinations | Model as one combination asset/program with component references. | Component relationship UI is not implemented. | provisionally usable | Yes |
| Indication-specific development state | Row rule owned by [`entities-and-rows.md`](./entities-and-rows.md#row-splitting): a population or comorbidity difference alone does not establish a separate row. | One development state per row; may multiply rows. | assumption at risk | Yes |
| Combined Phase 1/2 trials | Use the registry-backed `Phase 1/2` development stage directly; do not collapse into Phase 1 or Phase 2. | None; `Phase 1/2` is a distinct registry stage (ADR-0013). | provisionally usable | No |
| Silent pipeline removal | Do not infer discontinuation from disappearance; keep prior status until evidenced. | Snapshot cannot represent "quietly dropped". | provisionally usable | No |
| Completed trial with unclear program continuation | Keep program status as-is; a completed trial is not discontinuation. | No trial-vs-program distinction in status. | provisionally usable | No |
| Country-specific approvals | Record `Approved` when approved by a tracked regulator; note jurisdiction in sources. | No per-jurisdiction approval fields. | assumption at risk | Yes |
| Device or injector differences | Provisionally same program unless it is a distinct configuration; document. | No device granularity. | open until pilot | Yes |
| Field-level provenance | Use record-level `metadata.sources` collectively covering key claims. | Sources attach to the record, not to fields. | assumption at risk | Yes |
| Unclear primary development company | Choose a defensible principal entity; log the ambiguity. | Single `companyId` forces a choice. | open until pilot | Yes |
| Same asset with overlapping indication scopes | Row rule owned by [`entities-and-rows.md`](./entities-and-rows.md#row-splitting); indication-content rule owned by [`source-and-entry-policy.md`](./source-and-entry-policy.md#population-and-comorbidity-versus-indication). Unresolved overlap is deferred, not merged or split arbitrarily; `npm run data:probe:indication-scope` reports candidate rows for review. | Overlap can create ambiguous duplicate rows. | open until pilot | Yes |
| Regulatory state display | Store registry-backed regulatory states separately from development stage. | Current UI does not display regulatory state. | provisionally usable | Yes |
| Diagnostic stress-test archives | Keep diagnostic references outside production aggregate generation. | Archives are not golden expected output. | provisionally usable | No |
| Regimen display | Store regimens separately from pipeline programs. | Current UI does not display regimens. | provisionally usable | Yes |
| Device, procedural, or bariatric-surgical candidates | Do not store under the current contract; disposition as DEFERRED with administration-contract expansion as the re-entry trigger. | The `administration` contract (`route`, `dosageForm`, `dosingInterval`) presumes a drug product; a device or procedure has no route/dosage-form representation, so this is not a scope decision that a `scopeClass` value can resolve — see [Data Protocol §Dataset scope](./README.md#dataset-scope). | open until pilot | Yes |
| Cross-company entity resolution | Use external names for other companies and their assets. | No global company/asset graph, alias registry, or automatic linking. | open until needed | Yes |
| Dose-level regimen arms | Merge dose, dose-ratio, titration, cohort, and trial-arm variants into one component-level regimen; for example, represent `bimagrumab + semaglutide` once. Use `configurationKey` only for an officially defined product or regimen configuration that remains distinct independently of arm dosing. | Dose-level arms belong to the future Clinical Evidence Arm layer; the current regimen registry has no arm model. | provisionally usable | Yes |
| Required background/concomitant therapy with unconfirmed component | Classify as an add-on/background-therapy program, not focal-asset monotherapy; do not invent a regimen component; defer the specific indication until an official source both names the exact background or concomitant product and confirms it as a distinct development configuration — a named but protocol-required standard-of-care background therapy remains background therapy and does not resolve the deferral. Disposition as DEFERRED. **Two independent re-entry paths**: (1) if a later official source confirms the co-administration as a distinct regimen configuration, reclassify under the **current** model as an ordinary Regimen record — no contract change needed for this path; (2) if it remains an unconfirmed add-on/background therapy with no distinct-configuration evidence, it stays DEFERRED until a **joint Company/Pipeline and Clinical Evidence structured background-therapy representation** is built. | Neither domain can structurally represent a background/add-on **intervention relationship** today. Company/Pipeline has no field expressing that a focal asset is developed on top of a named background therapy — `assetType`, `components`, and Regimen records exist but none encodes this relationship, and classification is a research-time judgment applied before row creation, not a stored field. Clinical Evidence can record it as free text on `arm.intervention` / `study.population` (ADR-0033) but has no structured background-therapy Arm **role** — roles are exactly `experimental \| placebo \| active comparator \| other`. | assumption at risk | Yes |
| Platform or master-protocol nested sub-studies | Attribute only the source's explicitly nested indications or sub-studies to the asset; do not infer unlisted indications from the trial's general population. | No `assetType` value; classification is a research-time judgment applied before row creation, not a stored field. | provisionally usable | No |
| Clinical Evidence: substudy and cohort representation | Store a substudy as a separate Study only when it has its own distinct registry identity; otherwise omit substudy- or cohort-specific results that cannot be mapped without treating a cohort as an Arm or inventing a registry identity. | An Arm represents a protocol-defined treatment configuration, not a cohort; Study has no parent/child or cohort structure, and globally unique `registry\|id` prevents multiple Study records from sharing a master-protocol identity. A future schema review must decide whether and how study hierarchy or cohort identity belongs in the model, without presupposing an implementation (ADR-0036). | assumption at risk | Yes |
| Clinical Evidence: protocol-defined Arm versus pooled or derived analysis group | **Resolved by schema v2.0 (ADR-0037).** Model a source-reported pooled, derived, or starting-dose group as a study-scoped `AnalysisGroup` over its member protocol Arms, and anchor the Outcome via `analysisGroupId`. Still never invent Arms, nest groups, or redistribute a pooled value across members. | Was: Outcome could reference only `armIds`. Remaining limit: an AnalysisGroup is study-scoped and carries a single-unit result — a comparison *between* groups, or a group spanning Studies, is still unrepresentable. | provisionally usable | No |
| Clinical Evidence: multi-focal or external-asset study anchoring | Storage ownership stays with the singular `companyId`/`assetId` anchor **by design** (ownership, not scientific primacy). An internally resolvable comparator/component Arm must link with `companyId` + `assetId` **across companies** (ADR-0037), and reciprocal asset → studies discovery is served by the derived projection `data/generated/clinical-evidence-asset-studies.json`. Still omit a result whose focal anchor is genuinely ambiguous. | Multi-anchor storage remains deliberately unsupported; discovery is a derived projection, not a second anchor. A shared registry identity across sub-studies or multiple focal assets under one identifier remains unrepresentable (row above). | provisionally usable | No |
| Clinical Evidence: comparison between analysis groups | Omit a group-versus-group or group-versus-arm comparison; store only the single-unit results the source reports for each analysis unit. Report it as a deferred schema case (workflow §5.1). | An Outcome anchors to exactly one `analysisGroupId` and an analysis-group Outcome carries an `arm-level` (single-unit) result, so a between-group effect estimate has no representation (ADR-0037). | open until pilot | Yes |
| Clinical Evidence: endpoint testing order and multiplicity | Store the confirmed `role` (`primary`, `co-primary`, `key-secondary`, …). Do not encode the prespecified testing sequence, alpha allocation, or gatekeeping structure. | `role` states an endpoint's role, not its ordered position in a multiplicity-controlled testing hierarchy (ADR-0037, deferred). | open until pilot | Yes |
| Clinical Evidence: cross-study pooled analyses | A result spanning multiple Studies is not entered. Within one Study, a source-reported pooled group is now representable as an `AnalysisGroup` (ADR-0037). | `Outcome` has a single required `studyId` with same-study containment, and `AnalysisGroup` is deliberately **study-scoped**: there is still no evidentiary unit above one Study (Preflight B FM-2; ADR-0036, ADR-0037). | open until pilot | Yes |
| Clinical Evidence: result maturity conflates finality and venue | Choose the single most decision-relevant `maturity` value and record the other axis in `metadata.sources`/`sourceType`; map a regulatory-sourced result to the closest venue value. | The `maturity` enum mixes an evidence-finality axis with a source-venue axis and has no regulatory value (Preflight B FM-5). | open until pilot | Yes |
| Clinical Evidence: semantically duplicate Arm/AnalysisGroup/Endpoint records | Reuse an existing id rather than authoring a semantic duplicate; a minimal validator check rejects obvious identical duplicates (same study plus normalized identity fields). | The outcome semantic key trusts Arm/AnalysisGroup/Endpoint ids as unique; non-identical paraphrase duplicates still bypass detection, so the reuse rule is the primary control (Preflight B FM-10). | assumption at risk | Yes |
| Clinical Evidence: estimand and analysis-population vocabulary drift | Preserve the source-reported text verbatim. Canonicalization (casing, punctuation, `estimand` suffix, standard analysis-set abbreviations) is applied to the semantic key and grouping only, so `"Treatment-policy estimand"` and `"Treatment policy estimand"` are one estimand (ADR-0037). The vocabulary stays open. | Canonicalization is alias-table-driven and structural; it cannot reconcile two genuinely different phrasings of the same estimand that share no canonical form. | provisionally usable | No |
| Clinical Evidence: study grouping (extension, rollover, core + OLE) | Store each as a separate Study with no stored parent/child linkage; state the relationship in the research report. | No `parentStudyId` / `studyGroupId`; a core trial and its extension cannot be presented as one arc (deferred from ADR-0037). | assumption at risk | Yes |

## Module B: Contract readiness classification

These classifications use the first two operating companies, Ascletis Pharma
and Zealand Pharma, as readiness evidence only. They do not change company data
or the current protocol. They were recorded for the earlier baseline and carry
forward unchanged into Contract 1.2 (ADR-0030, ADR-0053).

| Issue | Classification | Example | Current handling | V1 decision | Reason |
| --- | --- | --- | --- | --- | --- |
| Over-entered indication from a planned later-stage marker | data correction already resolved | Zealand petrelintide originally included `Chronic weight management` while the active Phase 2 evidence supports obesity/overweight and the broader weight-management wording belongs to planned Phase 3 work. | PR #11 removed the over-broad indication and regenerated aggregates. | keep as-is | This was a data-entry error, not a contract gap. |
| Official pipeline stage marker versus trial-initiated stage/status | current contract supports this after Module C annotation | Zealand petrelintide has a sponsor-declared Phase 3 chronic weight-management program with planned operational state; petrelintide / CT-388 has a Phase 2 registry entry that is not yet recruiting; Ascletis ASC35 has IND clearance but no started Phase 1 trial. | Store the most advanced official current `development.stage` and preserve evidence basis or operational state separately with `development.stageBasis` and `development.stageOperationalState`; keep regulatory details in `regulatoryStates`. | keep as-is for v1 | Module C added the smallest v1 annotation needed to avoid conflating sponsor-declared stage, regulatory-development milestone, clinical phase, and operational state. |
| Adjacent non-GLP-1 inclusion rationale | Resolved by Contract 1.2 `scopeClass` (ADR-0053) | Zealand petrelintide is an amylin analog tracked as a direct obesity competitor; Ascletis amylin assets appear as GLP-1-based fixed-dose combinations or regimens. | The required, durable `scopeClass` field replaces report-level rationale for why a non-GLP-1 row is tracked. | resolved | See [Data Protocol §Dataset scope](./README.md#dataset-scope); no further schema change needed. |
| Investigation classification tracking | v2 schema/backlog candidate | Zealand survodutide, ZP6590, glepaglutide, and dasiglucagon were reviewed and excluded; classifications are currently reported in the research output only. | Do not store investigation classifications in operating data; report each surfaced entity as entered, merged, deferred, or excluded, with a reason. | defer to v2 | The operating snapshot should stay clean for v1, but future refreshes would benefit from a lightweight classification ledger. |
| Principal developer versus originator/licensor/partner company | current contract supports this | Zealand petrelintide and petrelintide / CT-388 keep Zealand as principal with Roche in `relationships`; survodutide is excluded from Zealand operating data because Boehringer Ingelheim is solely responsible for global development and commercialization. | Use singular `companyId`; store supported partner roles in `relationships`; external companies stay external names. | keep as-is | ADR-0018, ADR-0019, and ADR-0022 cover the observed cases without requiring schema changes for v1. |
| Fixed-dose combination versus regimen handling | current contract supports this | Ascletis ASC30_39 FDC and ASC36_35 FDC are combination product records; Ascletis ASC37 plus ASC36 is a regimen; Zealand petrelintide / CT-388 is represented as a fixed-dose combination. | FDC/co-formulation products are pipeline programs with components; independently administered products are regimen records. | keep as-is | ADR-0016 and ADR-0017 handled both companies' examples. |
| Source-level versus field-level provenance | v2 schema/backlog candidate | Zealand and Ascletis records often use one source for pipeline status and another for route, phase, or regulatory state. | Store record-level `metadata.sources` collectively covering key claims. | defer to v2 | The current contract is sufficient for v1 validation, but field-level attribution would reduce ambiguity during future audits. |
